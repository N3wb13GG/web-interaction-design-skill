# Webの選択・ドラッグ・タッチ操作

## 制限の範囲

- 制限は依頼された要素と操作に限定する。対象候補は画像、文字のないアイコンボタン、施工前後の画像とラベル。通常の文章、文字付きボタン、リンクには既定の操作を残す。
- 対象をクラスまたはデータ属性で明示する。アイコンボタンのアクセシブルな名前、フォーカス表示、タップやキーボードでの起動を維持する。ARIAの名前と表示テキストを区別する。
- 入力欄と編集可能な領域では、選択、コピー、貼り付け、長押しメニューを維持する。保存防止の保証として案内せず、ページ上の操作を制限する機能として説明する。

## 実装と切り分け

- 対象だけに user-select: none と Safari 向けの -webkit-user-select: none を適用する。iOS Safari の長押しメニューには -webkit-touch-callout: none を使う。contextmenu の既定動作を取り消す際も対象内に限る。
- ドラッグの半透明プレビューと範囲選択のハイライトを区別する。前者には必要に応じて draggable=false、-webkit-user-drag: none、dragstart の取り消しを使う。画像付きリンクでは親リンクがドラッグ元になる場合も調べる。
- 文章から画像をまたいだ範囲選択は、画像に選択制限があってもブラウザー内の選択範囲に含まれ得る。その再ドラッグによる画像プレビューも制限する要件なら、dragstart 時に Selection の範囲と対象要素の交差を調べる。文章だけの選択・ドラッグと入力欄は許可する。
- タッチイベントの既定動作をページ全体で取り消すと、スクロールやピンチズームを妨げる。個別の操作だけに制限を適用し、通常タップとリンク遷移を確かめる。

## スマホでの確認

- iPhone Safari と Android Chrome で、通常タップ、対象の長押し、本文の範囲選択、入力欄の貼り付けを試す。デスクトップでは右クリックと、画像・画像付きリンク・選択済み文章から始まるドラッグを分けて試す。
- スマホでは、選択・長押しの制限を追加した箇所で、タップ・スクロール・入力が引き続き使えることを確認する。

# モバイルの固定ヘッダー・モーダル・Safari tint

スマホの高速スクロールでヘッダーが追従しない、モーダルの開閉で意図しないフォーカスやキーボード表示が起きる、または iOS Safari の上下ブラウザー領域の色が意図と違う場合に使う。対象の問題に関係する節だけ適用し、既存実装・再現条件・対象ブラウザーを確認する。

## 高速スクロールと固定ヘッダー

- `sticky` とスクロールコンテナー、祖先の `overflow`・`transform`・`filter`・`contain`、安全領域と描画位置を調べ、実際のずれを再現する。祖先の transform 等は fixed の基準も変え得る。
- ビューポートへの常時固定が要件であれば、`position: fixed; top: 0` を候補とし、本文にヘッダーの実高さと `env(safe-area-inset-top)` を含む余白を確保する。既存のレイアウト・重なり順・横向き・ブラウザー UI の伸縮に合わせ、数値を決め打ちしない。
- 固定要素の祖先に不要な transform を残さない。登場アニメーションは transform / opacity の短い一回限りとし、固定の追従・子要素の配置に与える影響を確認する。`prefers-reduced-motion` に対応する。

## モーダルのフォーカス

- 開いたときの入力先は画面の目的に応じて検討する。入力欄が複数ある場合は、いずれの入力欄にも自動フォーカスしない。ダイアログ本体も初期フォーカス先にしない。
- ネイティブモーダルの `showModal()` は `autofocus` がなくても初期フォーカスを移す。フォーカスをどこにも置かないと保証せず、必要ならダイアログ内の適切な非入力要素を検討する。意図しないキーボード表示を避けつつ、モーダルを支援技術に通知する。
- 閉じた後、タッチ操作ではブラウザー標準の元の要素への自動フォーカス復帰を抑える。キーボード操作では元の操作位置へのフォーカス復帰を維持し、モーダル内の移動と Escape による終了も維持する。`close()` による復帰やスクロールを確認し、支援技術や外付けキーボードで操作位置を見失わずに続行できる方法を検証する。
- `inert` の一時付与や `blur()` による復帰解除はブラウザー挙動に依存し、フォーカス喪失や読み上げの問題を起こし得る。無条件にコピーせず、既存の inert 状態、即時復元、閉じるアニメーション、入れ子、アンマウント時の処理を検証する。ページ全体のフォーカス表示を一律に無効化しない。`pointer: coarse` はタッチ操作や支援技術の利用有無を確定しない。

## iOS Safari のブラウザー領域

iOS 26 以降の Safari は画面端の要素から色を推定するため、`theme-color` やページ背景の変更だけでは tint を指定できない場合がある。上下それぞれ画面端近くに色付き要素を置き、透明なマスクで見えなくする回避策がある。これは公開 API ではなく Safari のヒューリスティックに依存し、OS・ブラウザー・配置によって結果が変わる。

### tint の実装

- 既存の tint や重複する画面端要素を先に確認する。色は対象 UI の背景に合わせ、テーマ変更にも追従させる。ブラウザー領域を透明に保ちたい場合は、着色要素を無条件に追加しない。
- 必要に応じて React 向けの `assets/SafariBrowserTint.tsx` と `assets/safari-browser-tint.css` をコピー・適応する。React 以外では同じ構造と CSS を移植する。既存の上部専用 `SafariTopTint` も利用可能。
- 不可視プリセットの出発点は画面幅の 89%、高さ 11px、上端から 4px、下端から 3px。**パネル幅ではなくビューポート幅が基準**。親の transform、overflow によるクリップ、固定位置の基準や重なり順を確認する。数値は検証済みの出発点であり保証ではない。
- `showModal()` のダイアログなどトップレイヤーがある場合、その内側かつ画面全体を基準にできる位置へ配置する。狭いスライドパネルの中に `width: 89%` を置くとパネル幅基準になり得る。開閉アニメーションやスクロール、閉じた後の色の復帰も確認する。
- ネイティブの popover を開くと下部 tint が意図せず変わる場合がある。popover はトップレイヤーに表示され、画面全体の透明な `::backdrop` が画面端の色判定に影響する可能性がある。背景の暗転が不要なら、対象の popover に限定して `.user-panel::backdrop { display: none; }` を試す。すべての popover や dialog に一律適用せず、暗転が必要な UI は維持する。
- LOL Sniper のユーザーメニューでは、この指定後にメニューを開いても下部 tint が変わらなくなったことをユーザーが確認した。Safari の色判定に対する回避策の一例であり、すべての iOS・Safari バージョンでの有効性は保証しない。
- tint は装飾であり、入力を遮らず読み上げ対象にしない。対応しない環境では非表示にする。上下を別々に使え、必要な位置だけ指定する。

## 検証

popover の backdrop を変更した場合は、対象メニューの開閉、外側タップによる終了、Escape、フォーカス操作と、iPhone Safari で開閉前後の tint を確認する。

固定ヘッダーは実機で高速スクロール、上下端、向き変更とセーフエリアを確認する。モーダルはタッチ、外付けキーボード、スクリーンリーダーそれぞれで開閉、初期・復帰フォーカス、キーボード表示、スクロール位置を確認する。


iPhone の実機 Safari で、対象の iOS バージョン、ライト・ダーク、画面上下、縦横、開閉中・開閉後、縮小モーションを確認する。表示が違うときは viewport 基準の幅、端からの距離、高さ、マスク、スクロールや transform によるクリップ、最上位レイヤーを順に調べる。デスクトップやビルド成功だけでは tint を検証できない。実機未検証なら明記し、成功を断定しない。
